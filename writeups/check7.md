## 2. 本机更大拓扑与路由

```text
C1 (80/8) -- R1 -- R2 -- R3 -- S1 (50/8)
C2 (81/8) --/             \-- S2 (51/8)
```

所有节点运行在同一 WSL 中。四个端点是 C1=80.6.5.4、C2=81.6.5.4、S1=50.9.8.7、S2=51.9.8.7。C1 <-> S1 与 C2 <-> S2 同时传输。R1-R2 的接口为 10.0.12.1/10.0.12.2，R2-R3 为 10.0.23.2/10.0.23.3。

| 节点 | 直连路由 | 其他目标的下一跳 |
|---|---|---|
| R1 | 80/8→client1；81/8→client2 | 50/8、51/8→east，经 10.0.12.2 |
| R2 | 中间转发 | 80/8、81/8→west，经 10.0.12.1；50/8、51/8→east，经 10.0.23.3 |
| R3 | 50/8→server1；51/8→server2 | 80/8、81/8→west，经 10.0.23.2 |

端点分别以各自所在网络的 .0.0.1 为默认虚拟网关。每条路由及动态分配的物理 UDP 端口都完整记录在 bigger/results.json 的 routers、endpoints、commands 和 links 中。

帧记录显示源端 TTL=128，经过三台路由器后抵达端点的 TTL=125。中间两段链路观测到 127 与 126，符合逐跳减一。该结果来自代理实际收到的数据，不是手填的示意值。

## 4. 抓帧与丢包恢复

为避免抓系统网卡权限依赖，本机实验在外层 UDP 隧道代理处记录内层以太网帧，写入标准 Ethernet pcap。每帧最多保存 96 字节，原始帧长度也保留；这可检查 ARP、IP/TCP 首部，不能用来重建完整文件。

定点丢包位置：stanford 链路，主动丢弃 1 帧。该链路观测到重复的数据序号范围 1 次，随后两个接收文件都与预期一致。这里只主动丢一次，不把它描述为固定百分比丢包实验。

正常回环运行也可见个别重复序号范围；它们可能对应本机调度和超时重传，不能将未注入丢包解释为绝无重传。实验工具没有代替 TCP 补发数据。

## 5. 创意项目：聊天与校验文件

chat.py 启动官方 tcp_eth_udp 子进程，将应用消息写入其标准输入，并从标准输出接收对方数据。应用字节实际经过自己的 ByteStream、TCP、NetworkInterface 与 Router；Python 没有改用系统 TCP 建立另一条数据连接。

应用用一行 JSON 定义一条消息，支持 UTF-8 聊天。文件通过 file-start、Base64 分块、file-end 三种消息传送；接收方逐块计算 SHA-256，核对字节数后才发布文件。

```python
if (state['received'] != state['size'] or
    state['hash'].hexdigest() != state['sha256']):
    raise ValueError('file length or SHA-256 mismatch')
```

最多 16 MiB/文件、4 个在途文件，限制单行长度；拒绝路径穿越，使用独立 .part 临时文件，验证后发布且不覆盖已有文件。8 项协议检查覆盖二进制、空文件、中文、损坏、路径和大小边界。

本机聊天室两个方向均收到 Hello 消息，并各接收 1 MiB 文件，收据、实际文件和哈希一致。接收文件原始内容留在 build/check7-chat-final，提交的证据保留聊天日志、收据、哈希和首部抓帧。

## 7. 三台电脑实测

| 角色 | Windows 地址 | Ubuntu 内部地址 |
|---|---|---|
| 本机路由器 | 10.200.49.154 | 172.18.80.5 / WSL |
| 同学 A 客户端 | 10.200.54.254 | 192.168.226.128 / 虚拟机 |
| 同学 B 服务端 | 10.200.93.187 | 192.168.105.128 / 虚拟机 |

以上为真实外层地址。A 的 VMnet8 为 192.168.226.1，B 为 192.168.105.1；本机 WSL 使用 Windows 侧 172.18.80.1。所有程序使用同一份项目实现，参与者用 A、B 和本机用户代称，不声称三人独立协议栈互操作。未提供姓名或 SUNet ID，未虚构。

| 位置 | 本地 UDP | 物理发送目标 |
|---|---|---|
| A Ubuntu 端点 | 2080 | 192.168.226.1:12080（自己的 Windows） |
| A Windows 转发 | 12080 | 本机路由器 Windows 10.200.49.154:19080 |
| 本机 Windows 两侧转发 | 19080 / 19050 | WSL 172.18.80.5:9080 / :9050，另一端为 A/B Windows |
| B Windows 转发 | 12050 | 本机路由器 Windows 10.200.49.154:19050 |
| B Ubuntu 端点 | 2050 | 由首个收到的帧学习本机 Windows 应答地址 |

内层拓扑为 A(80.6.5.4) - 路由器(80.0.0.1 / 50.0.0.1) - B(50.9.8.7:80)。路由器将 80/8 直连到 ucla 接口，50/8 直连到 stanford 接口。外层 Windows 转发只搬运 UDP，不替代中间 C++ 路由器的 IP 选路。

A 和 B 的 UDP 预检各 3/3 通过，控制台回传与本机应答日志相互吻合。正式路由器随后记录两个方向的 TCP 数据。两份接收端 FILE VERIFIED 均为 1,048,576 字节，SHA-256 与确定生成的原文件一致：

```text
7e7a19f30c8d5d3555721c2923598ef422d464e896fe68906f63f48c91f414fa
```

接收记录 1：22d683cdf656426ba246fb1a482536eb-test-1MiB.bin

接收记录 2：cfbdb07f88d24cbe9d57ec1bd662bed9-test-1MiB.bin

两份原始控制台片段未单独标注 A/B，证据文件保留原顺序，没有强行给文件名分配方向；路由器双向数据记录与用户按两个端点回传的结果共同支持双向传输结论。记录分为用户回传和本机直接采集两类，不将回传写成远程自动读取。

本次没有从缺少完整载荷的日志推算文件哈希，也不把日志中含 ACK、首部和重传的字节和当成有效吞吐。三路由器和并发多连接实验仍属于前述本机拓扑，三台电脑实际使用的是一个路由器、两个端点。
